# Learning OS 敏捷开发与发布规范

来源：用户2026-11-13明确要求“保证能回滚情况下敏捷开发、不必过度校验、校验争取一分钟、开发备份并行、不涉及题库仅备份用户信息”。适用于后续项目工作。原Master需求仍保留；这里更新执行流程，不删业务验收，不把未测项标为通过。

## 1. 默认节奏

- 优先最短用户闭环，直接修真实问题；不每次重新调研全站、不为小改动启动设计研究。
- 先读取Git状态、最近开发记录和相关代码；不得覆盖其他任务未提交修改。
- 立即记录生产旧image ID/tag、配置与一条可执行回滚命令；开发和符合范围的备份并行。
- **受影响校验目标≤60秒**：相关测试 + 必需的受影响构建/类型检查 + diff检查。普通小修不运行全量后端/全设备截图矩阵，不重复构建同一SHA。
- 60秒是目标，不是硬性截断命令或带已知故障发布的许可。认证/权限/数据迁移风险、失败用例有明确风险时，执行必要检查并解释超时原因。
- 代码冻结后只修发布阻塞，不加懒加载、依赖升级、全局换肤或新抽象；可选优化另立任务。
- 满足回滚和最小gate即可发布；线上健康+本次路径后交付，不为了文档重启/重建。
- 大功能先做一个真实纵切（例如题单→中段题→作答→返回），每批复用同一fixture和已通过结果，避免最后才发现核心恢复故障。

## 2. 按实际变更范围备份

| 变更 | 必须保留 | 默认不做 |
|---|---|---|
| UI/路由/静态资源，不改题库 |旧应用镜像/源码SHA，受影响配置/PWA，当前用户数据备份及schema/migration版本|重复导出QuestionAsset二进制、题库/搜索重建数据或全库2.87GB备份|
| 账号偏好/学习功能 |以上 + 当前账号与学习表及FK依赖；迁移计划与受影响表结构|把“用户数据”误解为只备份auth_user/UserPreferences|
| 临时认证字段兼容增宽 |以上 + 相关认证元数据，兼容旧应用验证|因非破坏性增宽而反向缩列或覆盖上线后学习记录|
| 真正题库/题图/批量导入/删除 |变更对象数据和依赖/原图、可验证恢复材料；必要时扩大到完整数据库|强行按一分钟省略不可逆数据安全检查|

“用户数据”包括账号/认证所需信息、用户偏好、计时/任务/日志、学习记录、Attempt及错误子项、Note所在UserState、掌握/收藏/待复习、TimingSession、ReviewPlan、Marker、Erratum、Topic/FormulaMastery、用户试卷及Item、分享/恢复与其它用户所有数据和依赖。真实表由 `tracker/models.py`、`drill/models.py` 和当前认证模型/FK审计确定；不可直接凭此列表猜表名。

保留schema、migration清单、FK关系与当前题库引用版本；仅用户数据备份依赖题库未变且仍可用。`pg_dump`按明确表范围使用一致快照，必要表不能分批乱序拼接；以schema/依赖可恢复性为准，不把文件存在当成功。加密字段的解密密钥沿用安全存储与恢复机制，严禁进Git。备份失败阻止切换；不用全库恢复作为应用回滚，避免抹掉发布后学习记录。备份异步启动后检查退出码与产物，不提前宣称完成。

## 3. 选择最小有效校验

- 只改文档：链接/路径、diff与敏感信息检查；不构建、不部署。
- 单组件/样式：相关组件测试或一个真实浏览器路径、受影响前端构建（需要新产物时仅一次），必要视口；不跑全量PG。
- 路由/导航：测本次跳转与返回、前缀/deep link；不要顺便重测所有统计公式。
- 后端查询：相关API/权限/排序测试；性能问题用同fixture少量对照，不猜测数据库问题。
- 偏好同步/鉴权：必须覆盖账号隔离与失败场景，不能因小改动漏权限。
- 迁移：`migrate --plan`、影响表测试与回滚兼容性；破坏性迁移才做更重恢复演练。
- 某一case失败：先定位环境还是代码，只重跑失败与实际受影响范围。不要连续5次全量suite来寻找环境缺项。
- 全量suite只在明确必要门禁/跨域风险时运行，或适合的独立后台任务；不要与使用同数据库/共享产物的任务并行。
- 构建共用appearance bootstrap等产物时串行构建；测试、只读诊断与备份可并行。已验证的同一SHA产物直接发布。

## 4. 并行与沟通

- 小任务单Agent；多Agent只用于明确独立模块，先约定文件所有权与接口。
- 共享Tokens/App/router/认证/模型迁移由主Agent统一；禁止多个Agent竞争全局CSS、reset或覆盖工作区。
- 子Agent交付：修改文件、核心结果、阻塞项、验证命令。不要复制整份用户要求/研究报告。
- 维护一份短发布台账：当前SHA、已通过gate、阻塞、生产tag、回滚。跨上下文从台账继续，不重做基线。
- 工作中每≤60秒给简短有事实的进展；不要反复请求已授权的部署确认。

## 5. 发布与记录

1. 确认旧镜像/config存在，备份完成，Git变更范围清楚。
2. 仅一次最终受影响验证；记录真实耗时和结果，不造假，不追加可选优化。
3. 已授权部署直接执行：应用/worker一致；只有需要的迁移；`nginx -t`后才reload；不替换无关站点。
4. 使用真实存在的健康入口 `/accounts/login/`，不要猜 `/healthz`；确认Dockerhealthy、queue成功。
5. 验证一次本轮真实路径；严重故障用已记录旧镜像回滚，保留新的学习数据。
6. 提交/推送源码与简短交付记录：版本、结果、回滚、已知风险。文档提交不再发版。
7. 未有实体设备就标记Safari/PWA实机未测；网络出口403与应用错误区分；不得以加更多测试掩盖交付拖延。
