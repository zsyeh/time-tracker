## 已定位的差异

1. **JSON正文传输是已测量瓶颈。** 5次`heatmap_api.encodedBodySize == decodedBodySize == 307254`字节，未压缩；正文传输46–673ms，而响应头约107–123ms。JS为349541字节压缩→1056999字节解压，说明静态脚本压缩有效，JSON未启用相同压缩。原after第三次热图响应完整1744ms也明确包含网络正文尾部。
2. **数据到DOM没有新增600ms计算。** API完成至963个格子的第一格插入仅23–31ms；插入至RAF/布局121–138ms，主线程对应任务125–142ms。`shallowRef`与减少隐藏span没有在此阶段引入数百毫秒新工作。
3. **冷启动有独立代价。** HTML/脚本/CSS/解析到DCL约352–488ms，随后账号启动与recovery让热图请求从386–525ms开始。auth请求20–82ms、recovery20–25ms；这些等待不能称为题库SQL耗时。
4. **探针自身存在轮询延迟。** 首格RAF可见时间789/1209/1295/1413/1069ms，原脚本的locator+wait返回828/1403/1429/1452/1295ms，落后39–225ms。两种测量均保留，不把RAF候选等同于屏幕实际合成呈现。
5. **5次不是稳定P95。** 新5次原等待中位1403ms，较原after1950ms短，但不能证明原线上回归已消失，也不能脱离网络变化归因某一CSS改动。
