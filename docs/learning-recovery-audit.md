# Learning recovery audit (2026-11-11)

Production is the single writer at 47; IP HTTPS / + /drill/ + /ei/ share one origin and root-scoped auth cookies. Nginx rewrites workspace prefixes to the existing single Django/Gunicorn process. RainYun is an edge only. Current production image before this work: 20261111-reader-glass, c30cb6b3. No deployment/proxy changes are needed for source development.

QuestionView currently generates a new crypto timing key at mount and on each question change, POSTs begin, and cancels on route leave. The timer is driven by server starts_at + performance.now, but has no visibility pause/checkpoints. Refresh creates another QuestionTimingSession with a fresh five-second delay. Submission overrides client duration with server wall time. QuestionAttempt.time_spent_seconds feeds drill timing/trends/reports; this is NOT merely a UI counter. Older history (048aec4, dcd0308, e87ed80) introduced persistent start timestamps and attempt-duration aggregation; later tab-scoped keys lost reload recovery. Notes already have user-scoped local drafts, five-second server autosave and state_version conflict checks. Submission keys already deduplicate atomically, with Question row locking. Reuse these.

Timer TimeLog is independent: duration derives from explicit start/end, with 25-minute/12-hour validity and efficiency grading. Existing running sessions load from dashboard overview. Pausing its historical wall-time semantics would alter statistics; leave them unchanged, improve lifecycle refresh/drafts only. Neither a question checkpoint nor a resume bookmark creates a TimeLog or QuestionAttempt.

No existing per-user JSON preference/bookmark store is suitable: SiteConfiguration is global policy, RuntimeSettings writes instance .env, notes and auth-session storage must not be repurposed. Extend QuestionTimingSession with protocol-2 checkpoint metadata, and add a small user resume/lease record (no duplicate duration statistics table). An additive migration is required; DO NOT run on production without backup/review/explicit authorization. Legacy begin/cancel and legacy submissions must retain behavior, while protocol 2 uses confirmed foreground cumulative checkpoints and bounded leases. Historical attempts and reporting queries remain unchanged.

Risks: overlapping devices, late/offline uploads, stale restored question IDs, timing finalization vs retry races, lost final lifecycle events, user switch, PWA Home loops. Use user/workspace scopes, one foreground lease per user, monotonic snapshots+sequence, existing submission UUIDs, conservative freeze gaps, periodic checkpoints, validation and an explicit manifest launch marker. No offline Service Worker. Native iPad termination can lose at most the interval since the last successful local checkpoint; offline cold HTML loading cannot be guaranteed without an app shell cache.
